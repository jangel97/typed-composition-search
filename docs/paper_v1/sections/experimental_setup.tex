
\section{Experimental Setup}
\label{sec:experimental-setup}

We evaluate Typed Composition Routing (TCR) across multiple domains, language models, and routing strategies to answer three research hypotheses (Section~\ref{sec:hypotheses}). The evaluation is designed to isolate the effects of entity prediction, graph structure, and end-to-end routing performance.

\subsection{Domains}
\label{sec:domains}

We evaluate on five tool domains spanning infrastructure operations and e-commerce, covering a broad range of graph structures and tool registries (Table~\ref{tab:domain-stats}).

\input{figures/table_domain_stats}

The domains vary along three dimensions relevant to our hypotheses:

\begin{itemize}
    \item \textbf{Catalog size}: from 54 to 170 tools.
    \item \textbf{Type density}: entity types represent between 30\% and 94\% of the number of tools.
    \item \textbf{Graph sparsity}: average entity pruning ranges from 56\% to 87\%.
\end{itemize}

CI/CD provides a particularly informative case.
Although it contains 51 entity types for 54 tools (94\% type density), leaving almost no reduction in label space, it achieves the highest entity pruning (87\%).
This demonstrates that TCR derives its advantage from graph topology rather than simply reducing the number of prediction labels.

Tool registries for Kubernetes, Ansible, GitHub, and CI/CD are constructed from their respective API documentation and operational workflows.
The Shopify registry is derived from the Shopify Admin REST API and serves as a non-infrastructure domain to evaluate generality.

\subsection{Models}
\label{sec:models}

We evaluate four language models spanning different architectures and model sizes:

\begin{itemize}
    \item \textbf{Granite 4.1 8B}
    \item \textbf{Qwen3-14B}
    \item \textbf{GPT-OSS-20B}
    \item \textbf{Claude Haiku 4.5}
\end{itemize}

All models are evaluated off-the-shelf without fine-tuning.
Since TCR requires only entity type prediction, the approach is applicable to any language model capable of natural language understanding, regardless of whether it was specifically trained for tool use.

\subsection{Query Dataset}
\label{sec:query-categories}

The benchmark contains 140 manually curated queries distributed across the five domains (25--30 queries per domain).

Queries were manually authored by the first author for each domain based on realistic operational tasks supported by the corresponding tool registry.
For each domain, queries were written to cover six predefined routing challenge categories, with category counts chosen to ensure representation of each difficulty type while emphasizing clean queries as a baseline.
Ground-truth annotations (source type, target type, and expected tool sequence) were derived from the typed composition graph independently of any model outputs, and all queries were finalized before model evaluation began.
Queries were written individually rather than generated from templates.
The complete benchmark containing all 140 annotated queries, tool registries, and typed composition graphs will be released upon publication.

Queries are organized into six categories that exercise different routing challenges:

\begin{itemize}
    \item \textbf{Clean}: explicit requests with clearly identifiable entities.
    \item \textbf{Multi-hop}: workflows requiring three or more tool invocations.
    \item \textbf{Noisy}: realistic user requests containing irrelevant or distracting information.
    \item \textbf{Synonym}: alternative terminology referring to the same entity types.
    \item \textbf{Ambiguous}: queries where multiple interpretations are plausible.
    \item \textbf{Multi-path}: queries admitting multiple valid tool compositions.
\end{itemize}

Each query is annotated with

\begin{itemize}
    \item the ground-truth source entity type,
    \item the ground-truth target entity type,
    \item the expected tool sequence corresponding to the shortest valid path in the graph.
\end{itemize}

\subsection{Routing Strategies}
\label{sec:strategies}

We compare TCR against six representative routing strategies.

\begin{enumerate}
    \item \textbf{Baseline}: direct tool selection from the complete tool catalog via prompt-based selection.
    \item \textbf{Function Calling}: since modern LLM APIs increasingly expose native function-calling interfaces, we evaluate whether structured tool schemas improve routing compared to prompt-based selection. Tools are passed as OpenAI-compatible function schemas via the \texttt{tools} parameter.
    \item \textbf{Retrieval}: embedding-based retrieval selects the top-$k$ candidate tools before tool selection.
    \item \textbf{Graph}: Typed Composition Routing (ours).
    \item \textbf{Graph-Reverse}: target-first TCR variant with probability-based source selection using multiple model completions.
    \item \textbf{Oracle}: graph search using ground-truth entity types, providing an upper bound on routing performance achievable with perfect entity prediction.
    \item \textbf{Model-Types}: entity prediction only, without graph search, isolating type prediction quality (results reported in Tables~\ref{tab:type-prediction} and~\ref{tab:recall-decomposition}).
\end{enumerate}

Together, these strategies isolate the contribution of each component of the proposed formulation: prompt-based tool reasoning, native function calling, retrieval-based reduction, entity prediction, and graph composition.

\subsection{Evaluation Metrics}
\label{sec:metrics}

For end-to-end routing, we report precision, recall, and F1 computed over predicted and expected tool sets.

To evaluate structural validity, we additionally report the number of hallucinated tool invocations, defined as predicted tools that do not exist in the tool registry.

For entity prediction, we report

\begin{itemize}
    \item source entity accuracy,
    \item target entity accuracy,
    \item exact-match accuracy (both entity types predicted correctly).
\end{itemize}

These metrics allow the routing pipeline to be analyzed at both the semantic prediction level and the end-to-end execution level.

\subsection{Implementation Details}
\label{sec:implementation}

All language model calls use greedy decoding (temperature 0, max tokens 1024) with a single completion per query, making results deterministic across runs.
Prompts follow a structured format with equivalent engineering effort across strategies.
The baseline receives the complete tool catalog, with each tool listed by name and typed input/output signature, and is instructed to return a JSON list of tool names in execution order.
The function-calling strategy presents the same tools as OpenAI-compatible function schemas via the \texttt{tools} API parameter with \texttt{tool\_choice=auto}, and extracts predicted tools from the structured \texttt{tool\_calls} response.
The graph strategy receives the full list of entity types and returns a JSON object with predicted source and target types.
All strategies use identical decoding parameters.
The graph-reverse strategy uses 5 completions with probability-based aggregation for source selection.

For the retrieval strategy, each tool is represented as its name and typed signature (e.g., \texttt{list\_pods: (Namespace) $\rightarrow$ (PodList)}) and embedded using \texttt{nomic-embed-text-v1.5}.
The user query is embedded with the same model, and the top-10 tools by cosine similarity are presented to the language model using the same prompt template and decoding parameters as the baseline.
The value $k = 10$ was not tuned; it was chosen as a round number providing reasonable coverage across domains.

Query annotations were authored and verified by the first author.
All results are from single deterministic runs; since temperature is set to 0, repeated runs produce identical outputs.

\subsection{Research Hypotheses}
\label{sec:hypotheses}

The experiments are designed to test three hypotheses.

\paragraph{H1 (Decomposition Outperforms Direct Selection).}
Reformulating tool routing as entity prediction followed by graph search improves end-to-end routing performance compared to direct tool selection across models and domains.

\paragraph{H2 (Graph-Constrained Decision Space).}
The primary benefit of Typed Composition Routing arises from graph constraints rather than label-space reduction.
We quantify graph constraints using the entity pruning metric (Eq.~\ref{eq:entity-pruning}) and evaluate whether stronger graph pruning correlates with larger routing improvements.

\paragraph{H3 (Performance Decomposition).}
End-to-end routing performance decomposes into language model type prediction quality and graph reachability (Eq.~\ref{eq:recall-decomposition}), enabling routing errors to be attributed independently to semantic prediction or graph structure.
