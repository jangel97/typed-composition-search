\begin{abstract}
As LLM agents integrate with increasingly large tool ecosystems, tool routing---the task of determining which tools to invoke for a given query---becomes a major bottleneck. Existing approaches require the model to simultaneously identify relevant tools, infer valid multi-step compositions, and avoid hallucinated tool calls. We propose Typed Composition Routing (TCR), which decomposes this problem into two stages: the model predicts source and target entity types, while deterministic graph search over a typed composition graph reconstructs valid tool chains. Across four LLMs, five domains (54--170 tools), and 140 queries, TCR improves F1 in all 20 model--domain combinations (average $+0.32$) while eliminating nonexistent tool invocations. On a production MCP server with 1,060 tools, TCR reduces prompt tokens by 99.7\% and guarantees the absence of hallucinated tool calls by construction. Finally, a granularity study across two domains shows that type ontology design is a key performance lever whose optimal granularity depends on the capability of the entity-type predictor.
\end{abstract}

\section{Introduction}

LLM agents increasingly rely on external tools, but as catalogs grow from tens to thousands of APIs, tool routing becomes fragile. Direct tool selection requires the model to simultaneously identify relevant tools, infer valid multi-step compositions, and ensure structural correctness. As the catalog grows, each of these sub-problems becomes harder---and they interact, because an error in one propagates to the others.

Existing approaches leave both semantic and compositional reasoning entirely to the language model, without exploiting the typed structure already present in many APIs.

A simple observation motivates a different approach. Users naturally express intent in terms of domain entities rather than tools. A query like ``get the logs for pods in production'' refers to entity types---Namespace, PodLogs---without naming any tool. Given a typed API specification, valid tool chains can be recovered deterministically from the type graph. Entity types are explicitly signaled by user intent, whereas the tools that connect them are latent variables that must be inferred. By targeting entity types, the model classifies what the user already said rather than inferring what the user never mentioned.

\textbf{Typed Composition Routing (TCR)} addresses this by decoupling semantic reasoning from compositional reasoning. The model handles only (1)~\textbf{semantic reasoning}---predicting source and target entity types---while (2)~\textbf{compositional reasoning} is delegated to deterministic graph search over a typed composition graph, which reconstructs structurally valid tool chains. The composition graph is derived from typed API specifications, automatically when schemas expose input/output types (e.g., OpenAPI), or through lightweight manual annotations otherwise.

We make three contributions:
\begin{enumerate}
  \item A method that decomposes tool selection into entity-type prediction and deterministic graph search, providing compositional validity guarantees and eliminating nonexistent tool invocations by construction.
  \item Experiments across four LLMs and five domains demonstrate consistent improvements over direct selection (average F1 $+0.32$). On a production MCP server with 1,060 tools, TCR reduces prompt tokens by 99.7\% while eliminating hallucinated tool invocations.
  \item A study of ontology granularity across two domains showing that type granularity is an important design parameter whose optimal value depends on predictor capacity.
\end{enumerate}

\section{Method}

\subsection{Typed Composition Graph}

We model each tool as a typed transformation: a tool $t$ takes an entity of type $e_i$ and produces an entity of type $e_j$. The full tool registry then induces a directed graph $G = (E, T)$, where entity types form the nodes and tools induce directed edges between compatible types. Any valid multi-step workflow corresponds to a path through this graph.

\subsection{Routing Decomposition}

Given a natural language query $q$, TCR proceeds in two stages. First, a predictor identifies the entity types the user is referring to:
\begin{equation}
  f(q) \rightarrow (e_{\text{src}}, e_{\text{tgt}})
\end{equation}
Then, deterministic graph search enumerates all type-compatible tool chains connecting those types:
\begin{equation}
  \text{Compose}(G, e_{\text{src}}, e_{\text{tgt}}) \rightarrow \{[t_1, \ldots, t_l]\}
\end{equation}

This decomposition rests on an asymmetry: entity types are explicit in user queries (``pods,'' ``credentials,'' ``inventories''), whereas tool identities and their compositions are latent. This reduces the prediction space from hundreds or thousands of tools to a much smaller set of semantic types---the model classifies what the user already said rather than inferring what the user never mentioned. Because the graph contains only registered tools as edges, any traversal inherits a structural guarantee: every returned tool belongs to the registry and every adjacent pair is type-compatible by construction, unlike standard retrieval or direct LLM selection approaches, which do not enforce these guarantees. The candidate set can be used directly (when it is small enough) or passed to a second-stage LLM that selects from the narrowed list rather than the full catalog. This allows a downstream model to reason over a dramatically smaller search space without sacrificing valid compositions. Importantly, the graph search stage performs no language understanding or semantic inference; all semantic reasoning is confined to entity-type prediction.

\textbf{Example.} Consider the query \textit{``Get the logs for pods in the production namespace.''}  The predictor identifies Namespace as the source type and PodLogs as the target. Graph search finds the path Namespace $\rightarrow$ Pod $\rightarrow$ PodLogs, yielding the tool chain [\texttt{list\_namespaced\_pods}, \texttt{get\_pod\_logs}]---two tools the user never named. Direct selection would need to identify both tools and their ordering; TCR predicts only the chain endpoints and lets the graph fill in the rest. The predictor never needs to infer the intermediate Pod entity---it emerges naturally from graph traversal. Figure~\ref{fig:method} illustrates the full pipeline.

\subsection{Candidate Search Algorithm}

$\text{Compose}(G, e_{\text{src}}, e_{\text{tgt}})$ returns all tools that lie on type-compatible paths between source and target. The search must satisfy three properties: (1)~every returned tool belongs to at least one valid path from $e_{\text{src}}$ to $e_{\text{tgt}}$; (2)~every returned tool belongs to the registered tool catalog; (3)~self-loop tools on $e_{\text{tgt}}$ (e.g., delete or update operations on the target entity) are included even though they do not advance along a path.
Candidate search performs no semantic reasoning; it operates purely over the typed composition graph.

Exact enumeration of all path-participating edges is unnecessary for our setting. Algorithm~\ref{alg:candidate} describes a linear-time reachability-based approximation that produces exact results on K8s (21 types) and a near-exact superset on AAP (88 types, 3 extra tools on one type pair).

\begin{algorithm}[h]
\caption{CandidateSearch$(G, e_{\text{src}}, e_{\text{tgt}})$}
\label{alg:candidate}
\begin{algorithmic}[1]
\IF{$e_{\text{src}} = e_{\text{tgt}}$}
  \RETURN self-loop tools on $e_{\text{src}}$
\ENDIF
\STATE $G' \leftarrow G$ with self-loop edges removed \COMMENT{they preserve the current entity type}
\STATE $F \leftarrow$ forward-reachable nodes from $e_{\text{src}}$ in $G'$
\STATE $B \leftarrow$ backward-reachable nodes from $e_{\text{tgt}}$ in $G'$
\STATE $V \leftarrow F \cap B$
\STATE $C \leftarrow \{t \mid (u \xrightarrow{t} v) \in G',\; u \in V,\; v \in V\}$
\STATE $C \leftarrow C \;\cup$ self-loop tools on $e_{\text{tgt}}$
\RETURN $C$
\end{algorithmic}
\end{algorithm}

\section{Related Work}

Existing tool-routing methods fall into three broad categories. \textit{Direct selection} approaches train or prompt LLMs to choose tools from catalogs \citep{qin2024toolllm,patil2024gorilla,schick2023toolformer,du2024anytool}. \textit{Graph-constrained planning} adds structural guidance---ControlLLM~\citep{liu2024controlllm} uses a bipartite resource-tool graph for multimodal routing, while ToolNet~\citep{liu2024toolnet} and GNN4Plan~\citep{wu2024gnn4plan} incorporate co-occurrence or GNN-based graphs. \textit{Agent frameworks} such as HuggingGPT~\citep{shen2023hugginggpt} and ReAct~\citep{yao2023react} rely on open-ended LLM reasoning with no structural guarantees. What all of these share is a common prediction target: the tool itself. Rather than predicting tools directly, TCR predicts semantic endpoints and delegates composition to deterministic graph search.

\section{Experiments}

\subsection{Setup}

We evaluate on five benchmark domains---Kubernetes (135 tools), Ansible (108), GitHub (133), CI/CD (54), and Shopify (170)---plus a production-scale domain: the Ansible Automation Platform (AAP) MCP Server, with 1,060 tools and 50 entity types.

Four LLMs serve as type predictors: Granite 4.1 8B (IBM), Qwen3-14B (Alibaba), GPT-OSS-20B \citep{openai2025gptoss}, and Claude Haiku 4.5 (Anthropic). All are evaluated zero-shot, without fine-tuning. We compare against two baselines---direct selection (full tool catalog in the prompt) and embedding retrieval (top-10 tools by cosine similarity using nomic-embed-text-v1.5)---as well as an oracle that uses ground-truth entity types. All strategies are evaluated as candidate generators: each produces a set of tools for a query, and we report per-query precision (fraction of returned tools in the gold set), recall (fraction of gold tools returned), and their harmonic mean F1, macro-averaged across queries.

The benchmark comprises 140 manually authored queries for the five benchmark domains and 120 queries for AAP, each spanning six categories: \emph{clean} (direct, unambiguous requests), \emph{synonym} (paraphrased intents using different vocabulary), \emph{multi-hop} (queries requiring two or more chained tools), \emph{ambiguous} (underspecified queries with implicit context), \emph{noisy} (conversational or informal phrasing), and \emph{multi-path} (queries where multiple valid tool paths exist). This category mix tests robustness across the variation patterns that arise in real user inputs.

All queries and gold annotations were authored by the paper's authors: queries were written from API documentation without reference to the routing system, expected tool chains were determined by manual inspection of the type graph, and no annotations were revised after observing system outputs. We acknowledge that author-authored benchmarks may unintentionally favor the proposed decomposition; independently constructed benchmarks would strengthen the evaluation.

\subsection{Main Results}

Table~\ref{tab:main} summarizes the results. TCR improves F1 in every one of the 20 model--domain combinations, with an average gain of $+0.32$ over direct selection. The effect is statistically significant (Wilcoxon signed-rank $p < 10^{-6}$, $N{=}20$) and practically large: even the weakest model under TCR (GPT-OSS-20B at 0.83) outperforms the strongest baseline (Qwen3-14B at 0.58). No TCR output contains a nonexistent tool invocation. The oracle achieves F1\,=\,1.00 because gold tool chains were constructed by inspection of the type graph, so the graph covers every annotated chain by design; this upper bound reflects graph completeness rather than an empirical claim.

\subsection{Production Scale: 1,060 Tools}

At production scale, the cost of direct selection becomes prohibitive. Presenting all 1,060 tool schemas to the LLM requires roughly 25,000 prompt tokens per query. TCR sidesteps this entirely: the model receives only entity type names (${\sim}$66 tokens), and graph search generates candidates from the composition graph.

\subsection{Ontology Granularity Experiment}

The results above treat the type system as fixed. But how sensitive is routing quality to the granularity of the ontology? To find out, we constructed three ontology variants---coarse, medium, and fine---on both a K8s subset (17 tools, 128 queries) and AAP (1,060 tools, 120 queries), varying only the type system while holding tools and queries constant. On K8s, coarse uses 6 entity types (e.g., \texttt{Pod}, \texttt{Resource}), medium splits these into 13 types (distinguishing \texttt{Deployment}, \texttt{Service}, \texttt{Node}, etc.), and fine introduces 21 types with detail variants (\texttt{PodDetail}, \texttt{ServiceDetail}, \texttt{PodCreation}). On AAP, the three levels have 8, 50, and 88 types. Each query is annotated with source and target types for all three granularity levels; the same query text maps to different type-pairs depending on the ontology. Granite 4.1 8B and Claude Opus receive 10 few-shot examples per granularity level, automatically selected from training data with stratified sampling across source--target pairs to maximize type-pair coverage.

Tables~\ref{tab:gran-k8s} and~\ref{tab:gran-aap} compare two predictors of different capacity---Granite 4.1 8B and Claude Opus---against the oracle upper bound. With a perfect predictor (oracle rows), finer types are strictly better: candidate sets shrink and precision rises. The question is whether the predictor can keep up as the type vocabulary grows.

On K8s (Figure~\ref{fig:crossover}, left), both predictors improve monotonically with finer types, though the gap between Granite and the oracle widens: exact match drops from 77\% to 71\% as the vocabulary grows from 6 to 21 types. Opus matches oracle performance exactly (100\% exact match across all granularities). On AAP (Figure~\ref{fig:crossover}, right), the effect is more pronounced: Granite exact match drops from 61\% to 35\% at 88 types, though F1 still improves marginally (0.110 $\rightarrow$ 0.132) because the narrower candidate sets compensate. Opus, with sufficient capacity to classify all 88 types correctly, tracks the oracle throughout.

The mechanism: finer types reduce tools per type-pair ($7.5 \rightarrow 3.6 \rightarrow 3.2$ on AAP), but each new type needs few-shot coverage. With only 10 examples, Granite struggles to distinguish the 38 fine types added to AAP. The gap between Granite and Opus shows that the optimal granularity depends on predictor capacity: a sufficiently capable model always benefits from finer types.

\section{Discussion}

\textbf{Why is type prediction easier than tool selection?} Users say ``pods,'' ``credentials,'' or ``inventories''---entity types, not tool names like \texttt{list\_namespaced\_pods\_v1}. Because entity types align with how queries are phrased, predicting among tens of semantic types is substantially easier than selecting among hundreds of tool names. The consistent F1 improvement across all 20 model--domain combinations (Table~\ref{tab:main}) confirms this: the smaller target space ($|E| \ll |T|$) and graph reachability constraints reduce effective difficulty. Multi-hop queries benefit most: TCR predicts two types regardless of chain length.

\textbf{The granularity trade-off.} Finer types narrow candidate sets, but the benefit saturates if the predictor cannot keep up with the growing vocabulary. The practical lever is the ratio of candidate-set improvement to classification degradation. With a sufficiently capable predictor, finer types are always beneficial.

\textbf{Limitations.} TCR assumes typed API ecosystems; imperative operations without typed inputs/outputs fall outside the formulation. When multiple tools share the same type signature, intent-level disambiguation remains necessary. The current formulation handles only sequential workflows; multi-input dependencies would require hypergraph edges. Recall is bounded by annotation completeness: even with perfect type prediction, tools whose type relationships are not modeled in the graph will be missed. All benchmark queries were author-annotated; independently constructed benchmarks would strengthen the evaluation.

\section{Conclusion}

Decoupling semantic reasoning from compositional reasoning consistently improves routing quality ($+0.32$ F1 across 20 model--domain combinations), eliminates nonexistent tool invocations by construction, and scales to registries with over a thousand tools. The granularity experiment shows that the type ontology is itself a design lever: finer types always help when the predictor can keep up, but the optimal granularity depends on predictor capacity.

By reducing tool routing to classification over a small, fixed vocabulary of entity types (${\sim}$10--90 classes), TCR opens the door to lightweight predictors---in principle, a finetuned encoder could replace the LLM, reducing inference cost by orders of magnitude. We leave empirical validation to future work. Reference implementations are available as open source.\footnote{\url{https://github.com/jangel97/tcr-go}} More broadly, improving tool routing may require changing the prediction target: from tools to the domain abstractions that organize them.
