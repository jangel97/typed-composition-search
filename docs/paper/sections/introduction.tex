
\section{Introduction}
\label{sec:introduction}

Large Language Model (LLM) agents increasingly rely on external tools to answer questions and perform real-world tasks \cite{yao2023react, shen2023hugginggpt}. Modern tool ecosystems routinely contain tens or hundreds of APIs spanning cloud platforms, software development, infrastructure automation, and enterprise operations. As these ecosystems grow, \emph{tool routing} (determining which tools should be invoked to satisfy a user query) becomes increasingly challenging.

Existing approaches typically formulate routing as \emph{direct tool selection}: given a natural language query, the LLM selects tools directly from the full catalog \cite{li2025toolscope, qin2024toolllm}. This formulation requires the model to simultaneously identify relevant tools, infer multi-step compositions, and ensure that the resulting sequence is executable, all in a single unconstrained decision. As tool catalogs grow, this reasoning problem becomes increasingly difficult and may result in missed tool compositions or structurally invalid tool invocations.

We argue that the primary bottleneck is not merely the number of available tools, but the \emph{abstraction} itself. Direct tool routing conflates two fundamentally different reasoning tasks:

\begin{itemize}
    \item \textbf{Semantic reasoning:} What entities does the user refer to?
    \item \textbf{Compositional reasoning:} Which sequence of tool transformations connects those entities?
\end{itemize}

Treating both problems as a single prediction forces the LLM to reason simultaneously about meaning and execution.

We propose \textbf{Typed Composition Routing}, a reformulation of tool routing that explicitly separates these two reasoning problems (Figure~\ref{fig:approach}). Tools are modeled as typed transformations between entity types (e.g., \texttt{get\_pod\_logs}: \texttt{Pod} $\rightarrow$ \texttt{PodLogs}), forming a directed graph where entity types are nodes and tools are edges. Given a user query, the LLM predicts the source and target entity types, after which graph search deterministically recovers the corresponding tool composition.

Where direct tool routing maps a query to a tool sequence ($q \rightarrow \{t_1, \ldots, t_k\}$), Typed Composition Routing factorizes this into two steps: entity type prediction ($q \rightarrow (e_{\mathrm{src}}, e_{\mathrm{tgt}})$) followed by graph path recovery ($(e_{\mathrm{src}}, e_{\mathrm{tgt}}) \rightarrow [t_1, \ldots, t_l]$).
This decomposes the joint problem into entity type prediction, which leverages the LLM's strength in semantic reasoning, and graph path recovery, which is solved exactly by deterministic search.

We evaluate the proposed formulation across multiple language models, tool ecosystems, and routing strategies spanning a diverse collection of enterprise domains. Our experiments demonstrate consistent improvements over direct tool selection while providing a simple analytical decomposition that explains end-to-end routing performance in terms of entity prediction accuracy and graph resolution.

Our primary contribution is a new formulation of tool routing as typed entity reasoning over a composition graph, replacing direct tool selection with entity type prediction followed by deterministic graph search.
In support of this formulation:

\begin{enumerate}

\item We define a \textbf{typed graph execution model} in which entity prediction and graph search jointly recover valid tool compositions without training, fine-tuning, or embedding retrieval.

\item We derive an \textbf{analytical decomposition} of end-to-end routing recall into entity prediction accuracy and graph reachability, enabling routing failures to be attributed to either component.

\item We provide \textbf{empirical validation} across four language models, five tool domains, seven routing strategies, and 140 benchmark queries, demonstrating consistent improvements over direct tool selection while guaranteeing structural validity of all recovered tool chains.

\item We validate the approach on a \textbf{production-scale MCP server} with 1,060 tools, where the typed composition graph is derived automatically from OpenAPI specifications without manual curation, demonstrating that the formulation extends beyond hand-constructed evaluation domains.

\end{enumerate}
