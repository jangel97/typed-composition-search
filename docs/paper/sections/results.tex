\subsection{Main Results (H1)}
\label{sec:main-results}

Graph routing improves aggregate F1 in every model--domain combination (20/20, average $\Delta$F1 = +0.323).
Table~\ref{tab:main-results} presents the full comparison.

\input{figures/table_main_results}

The improvement is consistent across both models and domains rather than being driven by a particular benchmark configuration.
A pooled Wilcoxon signed-rank test over all 560 query-level paired comparisons confirms that the improvement is statistically significant ($p < 10^{-30}$; bootstrap 95\% CI on mean $\Delta$F1: $[+0.27, +0.37]$).
Because queries are grouped by model and domain, we also test at the model--domain level: 15 of the 20 aggregate comparisons reach significance at $p < 0.05$, and the aggregate $\Delta$F1 is positive in all 20.
The five non-significant comparisons correspond to the four CI/CD combinations and one Shopify combination, where baseline performance is already strongest and per-query effect sizes are smallest.
The largest gains appear where baseline performance is weakest (Ansible: +0.30 to +0.47, GitHub: +0.25 to +0.54), suggesting that graph constraints are most valuable when unconstrained tool selection is hardest.

Table~\ref{tab:strategy-comparison} compares all six routing strategies.
Retrieval-based routing provides modest improvements over the baseline but falls well short of graph routing.
Retrieval reduces the search space by filtering semantically similar tools, but does not enforce compositional validity.
The retrieved tools may be individually relevant but not necessarily composable into a valid workflow, which is precisely the problem that the typed graph addresses.

Graph-reverse routing, which uses multiple completions with probability-based source selection, performs well for smaller models but degrades for larger ones: GPT-OSS-20B yields F1 = 0.000 due to degenerate probability distributions, and Haiku-4.5 was not evaluated with this strategy.
These results suggest that the simpler target-first single-completion approach (Graph) is more robust across model families.

The oracle strategy (graph search with ground-truth entity types) achieves F1 = 1.000 across all five domains.
This result confirms that the typed composition graph has complete coverage, that every benchmark workflow is representable as a graph path, and that all remaining routing errors originate from entity type prediction rather than from limitations of the graph structure itself.

\subsection{Structural Validity}
\label{sec:hallucinations}

\input{figures/table_hallucinations}

As guaranteed by Proposition~1 and its corollary (Section~\ref{sec:tcr}), all graph-constrained strategies produce zero hallucinated tools across all model--domain combinations (Table~\ref{tab:hallucinations}).
This is not an empirical observation but a direct consequence of the graph formulation: graph search can only traverse registered edges, so no tool outside the registry can appear in the output.
In contrast, the baseline produces hallucinated tools in most runs, with totals ranging from 1 to 16 per model across domains.

The distinction matters for deployment.
A system that empirically produces few hallucinations may still hallucinate under distribution shift; a system that structurally cannot hallucinate provides stronger guarantees about the validity of generated tool sequences.


\subsection{Recall Decomposition (H3)}
\label{sec:recall-decomposition}

Table~\ref{tab:recall-decomposition} presents the recall decomposition from Eq.~\ref{eq:recall-decomposition}.

\input{figures/table_recall_decomposition}

The decomposition separates end-to-end routing performance into two independent factors: semantic prediction quality (whether the LLM identifies the correct entity types) and graph recoverability (whether the graph contains a valid path between those types).
The gap between predicted recall $\hat{R}$ and actual recall $R_{\text{actual}}$ has a median of 0.14 across all combinations, suggesting that these two factors capture a substantial portion of the observed routing behavior.

Rather than treating routing performance as a single opaque metric, the decomposition identifies where improvements should be directed: type prediction for the LLM, and graph coverage for the typed composition graph.

\paragraph{Graceful degradation.}
The decomposition also reveals that performance does not collapse when type prediction is wrong.
$R_{\text{wrong}}$ averages 0.292 across all combinations (range: 0.10--0.65), meaning incorrect type predictions still recover some of the correct tool chain rather than producing zero recall.

Neighboring entity types often induce overlapping paths in the typed graph.
When the LLM predicts a wrong but nearby type (e.g., \texttt{Deployment} instead of \texttt{Namespace}), the graph path from the incorrect type may still traverse through some of the correct tools, because the two types share downstream connectivity.
Densely connected regions of the graph provide more opportunities for partial recovery.


\subsection{Type Prediction Accuracy}
\label{sec:type-prediction}

\input{figures/table_type_prediction}

Table~\ref{tab:type-prediction} reports type prediction accuracy by query category.
Source prediction (0.70 overall accuracy) is harder than target prediction (0.80).
This is consistent with the intuition that users describe desired \emph{outcomes} (targets) more clearly than \emph{starting points} (sources), aligning with the semantic reasoning role assigned to the LLM in our formulation.

Clean queries achieve 81\% exact match, while ambiguous queries are hardest (25\%), since the target entity type is genuinely uncertain for these queries.
Synonym queries show reduced target accuracy (0.61); alternative terminology sometimes maps to the wrong entity type.
Improving entity prediction therefore translates directly into higher end-to-end routing performance, as the recall decomposition in Section~\ref{sec:recall-decomposition} confirms.


\subsection{Entity Pruning (H2)}
\label{sec:entity-pruning}

\input{figures/table_entity_pruning}

Table~\ref{tab:entity-pruning} reports entity pruning statistics per domain.
The median pruning across all domains is 75\%, meaning that for a typical query, three-quarters of entity types are eliminated as source candidates after target prediction.

CI/CD provides the clearest evidence for H2: with 51 types for 54 tools (near-parity), the type space offers almost no label reduction, yet entity pruning averages 87\% with a minimum of 76\%.
Even the hardest query in CI/CD constrains the source prediction to at most 12 out of 51 candidates.
The benefit of Typed Composition Routing therefore derives from graph topology rather than from reducing the number of prediction labels.

Entity pruning is a graph-topological property, independent of the language model.
It applies to any model performing type prediction.


\subsection{Token Efficiency}
\label{sec:token-efficiency}

We measure average prompt tokens per query across all model--domain combinations.
The baseline includes the full tool catalog (name and typed signature per tool) in the system prompt, averaging 1,823 prompt tokens per query (range: 847--3,033 across domains).
Graph-based routing presents only the list of entity types for type prediction, averaging 683 prompt tokens (range: 488--1,004).
The resulting 50--70\% reduction comes from replacing the full tool catalog with a smaller set of entity type labels.
The savings scale naturally with catalog size: as tool registries grow, the baseline must include proportionally more tool descriptions in the prompt, while graph routing presents only entity types whose count grows more slowly.
The relative advantage therefore increases with catalog size, directly addressing the scalability concern raised in Section~\ref{sec:introduction}.
