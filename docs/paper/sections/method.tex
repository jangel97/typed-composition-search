\section{Method}
\label{sec:method}

We reformulate tool routing as typed entity reasoning.
Instead of selecting tools directly from a catalog, we predict the \emph{entity types} that a query operates on and recover the tool sequence through graph search over a typed composition graph.

\subsection{Problem Definition}
\label{sec:problem-def}

Let $\mathcal{E} = \{e_1, e_2, \ldots, e_n\}$ be a set of \textbf{entity types} in a domain (e.g., \texttt{Pod}, \texttt{Namespace}, \texttt{Deployment} in Kubernetes).
Let $\mathcal{T} = \{t_1, t_2, \ldots, t_m\}$ be a set of \textbf{tools}, where each tool is a typed transformation:
\begin{equation}
    t_k : e_i \rightarrow e_j, \quad e_i, e_j \in \mathcal{E}
    \label{eq:tool-transform}
\end{equation}
That is, tool $t_k$ takes an entity of type $e_i$ as input and produces an entity of type $e_j$ as output.

\paragraph{Typed Composition Graph.}
We define a directed graph $G = (\mathcal{E}, \mathcal{T})$ where entity types are nodes and tools are edges.
An edge $t_k$ from $e_i$ to $e_j$ exists if and only if tool $t_k : e_i \rightarrow e_j$.
Multiple tools may connect the same pair of types, and a single tool may have multiple input or output types, producing multiple edges.

\paragraph{Tool Routing.}
Given a natural language query $q$, the goal is to produce an ordered sequence of tools $[t_1, t_2, \ldots, t_l]$ that, when composed, transforms some source entity into the desired target entity.
This sequence must be \emph{compositionally valid}: the output type of each tool must match the input type of the next.

\paragraph{Baseline Formulation.}
In direct tool selection, a model $g$ selects tools from the full catalog:
\begin{equation}
    g(q) \rightarrow \{t_1, \ldots, t_k\} \subseteq \mathcal{T}
\end{equation}
The model must simultaneously identify which tools are relevant \emph{and} determine a valid ordering.
With $|\mathcal{T}|$ tools, the decision space grows with the catalog size, and compositional validity is not guaranteed.

\paragraph{Our Formulation.}
We decompose tool routing into two steps:
\begin{enumerate}
    \item \textbf{Type prediction}: A model $f$ predicts the source and target entity types from the query:
    \begin{equation}
        f(q) \rightarrow (\hat{e}_{\text{src}}, \hat{e}_{\text{tgt}})
        \label{eq:type-prediction}
    \end{equation}
    \item \textbf{Graph search}: A deterministic search recovers the tool sequence:
    \begin{equation}
        \textsc{Path}(G, \hat{e}_{\text{src}}, \hat{e}_{\text{tgt}}) \rightarrow [t_1, t_2, \ldots, t_l]
        \label{eq:graph-search}
    \end{equation}
\end{enumerate}

The LLM handles semantic reasoning (what entity types does the user mean?), while the graph handles compositional reasoning (what tools connect those types?).


\subsection{Tools as Typed Transformations}
\label{sec:typed-tools}

Most tools in structured domains operate on well-defined entity types.
A tool consumes an entity of one type and produces an entity of another.
For example, in a Kubernetes tool catalog:

\begin{itemize}
    \item \texttt{list\_pods}: \texttt{Namespace} $\rightarrow$ \texttt{Pod}
    \item \texttt{get\_pod\_logs}: \texttt{Pod} $\rightarrow$ \texttt{PodLogs}
    \item \texttt{get\_pod\_node}: \texttt{Pod} $\rightarrow$ \texttt{Node}
\end{itemize}

A query like ``Get the logs for pods in the production namespace'' implicitly defines a path from \texttt{Namespace} to \texttt{PodLogs}.
The tools along this path (\texttt{list\_pods}, \texttt{select\_pod}, \texttt{get\_pod\_logs}) emerge from graph traversal rather than direct selection.


\subsection{Graph Construction}
\label{sec:graph-construction}

Given a tool registry with typed signatures, graph construction is mechanical:
for each tool $t_k : e_i \rightarrow e_j$, add a directed edge from node $e_i$ to node $e_j$ labeled $t_k$.
The resulting graph $G$ encodes all valid single-step transformations.
Multi-step compositions correspond to paths in $G$.

The graph is constructed once per domain and is independent of any language model.
No training, fine-tuning, or embedding computation is required.


\subsection{Path Recovery via BFS}
\label{sec:bfs}

Given predicted types $(\hat{e}_{\text{src}}, \hat{e}_{\text{tgt}})$, we use breadth-first search (BFS) on $G$ to find the shortest path from $\hat{e}_{\text{src}}$ to $\hat{e}_{\text{tgt}}$.
The edges along this path define the tool sequence.

BFS is deterministic and model-independent: given the same graph and type predictions, it always produces the same tool sequence.
This separates routing correctness into two independent factors: (1) whether the LLM predicted the right types, and (2) whether the graph contains a valid path.

When no path exists (disconnected types), the system returns an empty result rather than hallucinating tools.
Returning nothing is safer than returning structurally invalid tool sequences, particularly in infrastructure and operational domains.


\subsection{Entity-Based Routing}
\label{sec:entity-routing}

The full routing procedure works as follows:
\begin{enumerate}
    \item Present the LLM with the query $q$ and the list of entity types $\mathcal{E}$.
    \item The LLM predicts $(\hat{e}_{\text{src}}, \hat{e}_{\text{tgt}})$.
    \item BFS on $G$ recovers the tool path from $\hat{e}_{\text{src}}$ to $\hat{e}_{\text{tgt}}$.
    \item Return the ordered tool sequence along the path.
\end{enumerate}

The LLM chooses from $|\mathcal{E}|$ entity types rather than $|\mathcal{T}|$ tools, but the primary benefit is \emph{graph-constrained decision making}, not the reduced label count: after predicting one type, graph reachability constrains the valid choices for the other.


\subsection{Graph Constraint and Entity Pruning}
\label{sec:graph-constraint}

We quantify how much the graph constrains the decision space with the \textbf{entity pruning} metric.
For a given target type $e_{\text{tgt}}$, let $R^{-1}(e_{\text{tgt}}) \subseteq \mathcal{E}$ be the set of types from which $e_{\text{tgt}}$ is reachable via any path in $G$.
The entity pruning is:
\begin{equation}
    \text{pruning}(e_{\text{tgt}}) = 1 - \frac{|R^{-1}(e_{\text{tgt}})|}{|\mathcal{E}|}
    \label{eq:entity-pruning}
\end{equation}

A pruning value of 0.87 means that, given a target prediction, 87\% of source types are eliminated as candidates because they cannot reach the target through any valid tool composition.
This reduces the effective decision space for source prediction without any model computation.

Entity pruning is a property of the graph topology, not the language model.
It works identically regardless of which model performs type prediction.


\subsection{Research Hypotheses}
\label{sec:hypotheses}

We formulate three testable hypotheses:

\paragraph{H1 (Decomposition Outperforms Direct Selection).}
Graph-constrained entity prediction followed by graph search outperforms direct tool selection in end-to-end F1, produces zero hallucinated tools, and improves routing consistently across models and domains.

\paragraph{H2 (Graph Reduces Decision Space).}
Constraining tool routing to graph-reachable typed transformations reduces the effective decision space faced by the language model, leading to improved tool selection accuracy.
We measure this through entity pruning (Eq.~\ref{eq:entity-pruning}) and test whether greater search space reduction correlates with improved routing performance.

\paragraph{H3 (Performance Decomposition).}
End-to-end recall can be decomposed into type prediction quality and graph reachability:
\begin{equation}
    R = P_c \cdot R_c + (1 - P_c) \cdot R_w
    \label{eq:recall-decomposition}
\end{equation}
where $P_c$ is the probability of correct type prediction, $R_c$ is recall when types are correct, and $R_w$ is recall when types are wrong.
This decomposition separates model quality from graph quality and enables targeted failure analysis.
